# degoog — search aggregator

A privacy-focused search aggregator (github.com/degoog-org/degoog) with a plugin/extension
system, backed by Valkey (Redis) for caching. Runs alongside [SearXNG](searxng.md) so you can
compare the two metasearch approaches.

## At a glance
| | |
|---|---|
| **URL (domain)** | https://search.williampring.ca |
| **URL (raw)** | http://\<node-ip\>:30882 (NodePort) |
| **Namespace** | `apps` |
| **Deployed by** | Argo CD (GitOps) — ApplicationSet → `kubernetes/apps/apps/degoog/` |
| **Image** | `ghcr.io/degoog-org/degoog` — pinned; Renovate bumps it in the weekly `stateless patch updates` group |
| **Cache** | the shared Valkey LXC (`192.168.68.103`) — not in the cluster |
| **Storage** | 2Gi PVC `degoog-data` (local-path) → `/app/data` |
| **Health** | readiness probe on `/` (the same path Gatus checks) |

## Architecture
```
browser
  ├─ https://search.williampring.ca   (Ingress + Traefik + LE cert, via Tailscale)
  └─ http://<node-ip>:30882           (NodePort, raw)
       │
       ▼
  degoog pod  ──► Valkey LXC 192.168.68.103:6379   ← cache (external, survives rebuilds)
     │
     └─ /app/data  ──► PVC degoog-data (local-path)   ← settings/state
```

## Files (GitOps — one per resource)
```
kubernetes/apps/apps/degoog/
├── kustomization.yaml       # the resources below
├── deployment.yaml          # degoog (initContainer fix-perms → chown /app/data; Recreate; readiness probe)
├── degoog-service.yaml      # NodePort 30882 → 4444
├── ingress.yaml             # search.williampring.ca → degoog:4444 (cert degoog-tls)
├── pvc.yaml                 # degoog-data (2Gi, local-path)
└── externalsecret.yaml      # builds degoog-secret (DEGOOG_SETTINGS_PASSWORDS) from OpenBao homelab/degoog
(the Argo Application is generated by kubernetes/bootstrap/apps.yaml — manual sync, CreateNamespace=true)
```

Key wiring:
- degoog reaches Valkey through `DEGOOG_VALKEY_URL` (`redis://degoog:<password>@192.168.68.103:6379`), as its
  own ACL user `degoog`. The whole URL is in `degoog-secret`, from OpenBao `homelab/degoog` — not in git
  (when it moves, it moves to OpenBao — [`../platform/openbao.md`](../platform/openbao.md)).
- `DEGOOG_PUBLIC_INSTANCE: "false"` — not a public instance.
- `DEGOOG_SETTINGS_PASSWORDS` comes from the `degoog-secret` Secret.
- The Deployment listens on **4444**; the Service maps `4444 → NodePort 30882`; the Ingress
  routes `search.williampring.ca → degoog:4444`.

## Passwords & secrets

degoog has **one secret**, `degoog-secret`, with two keys: `DEGOOG_SETTINGS_PASSWORDS` (the password
that protects the settings/extensions UI) and `DEGOOG_VALKEY_URL` (the cache connection, password included). The value lives in OpenBao at `homelab/degoog` (not in git);
`externalsecret.yaml` tells External Secrets to build the Secret from it, and the Deployment reads it via
`secretKeyRef`. See [`../platform/openbao.md`](../platform/openbao.md).

```bash
# on a machine logged in to OpenBao (bao login -method=userpass username=william):
bao kv get -field=DEGOOG_SETTINGS_PASSWORDS homelab/degoog                       # read it
bao kv patch homelab/degoog DEGOOG_SETTINGS_PASSWORDS="$(openssl rand -base64 24)"  # change it (patch, never put —
                                                                                 # put replaces ALL keys)
# ESO refreshes within 1h — or now:
sudo k3s kubectl -n apps annotate externalsecret degoog-secret force-sync=$(date +%s) --overwrite
# the pod only picks it up on restart:
sudo k3s kubectl rollout restart deploy/degoog -n apps

# check the live Secret exists:
sudo k3s kubectl get secret degoog-secret -n apps
```

### Its Valkey user (one-time, before the first Sync that needs `DEGOOG_VALKEY_URL`)
The Secret can only be built once **both** keys exist in OpenBao — a missing key makes the ExternalSecret
fail and a new pod stop at `CreateContainerConfigError` (the running pod keeps working).
1. On the Valkey LXC (`192.168.68.103`), with a new random password (OpenBao UI → Tools → Random):
   ```
   ACL SETUSER degoog on >NEWPASS ~* &* +@all
   ACL SAVE            # if Valkey uses an aclfile; otherwise CONFIG REWRITE — see ../platform/redis.md
   ```
2. OpenBao UI → `homelab` → `degoog` → Create new version → add `DEGOOG_VALKEY_URL` =
   `redis://degoog:NEWPASS@192.168.68.103:6379` (keep `DEGOOG_SETTINGS_PASSWORDS` as it is).
3. Sync degoog, check a search works.
4. Then rotate the old shared `redis` user's password — it was inline in git, and only Immich uses it now:
   `ACL SETUSER redis resetpass >ANOTHERPASS` (+ save), update `REDIS_PASSWORD` in OpenBao `homelab/immich`,
   force-sync `immich-secret`, restart Immich.

## Troubleshooting
| Symptom | Cause / fix |
|---|---|
| `search.williampring.ca` 502/503 | Ingress backend port must be **4444** (matches the Service), not 8080 |
| Pod `0/1`, "Readiness probe failed" | degoog isn't answering on `/` — `sudo k3s kubectl logs deploy/degoog -n apps` |
| Pod CrashLoop, `/app/data` EACCES | the `fix-perms` initContainer chowns `/app/data` to 1000 — ensure it's present |
| Can't reach Valkey | the LXC at `192.168.68.103` is down, or the `degoog` user's password changed — `DEGOOG_VALKEY_URL` in OpenBao has to match ([`../platform/redis.md`](../platform/redis.md)) |
| Pod `CreateContainerConfigError`, `couldn't find key DEGOOG_VALKEY_URL` | the key isn't in OpenBao `homelab/degoog` yet, so the Secret has only the old key | add it (above, step 2), force-sync the ExternalSecret |
| Pod `CreateContainerConfigError`, `degoog-secret` missing | External Secrets couldn't build it from OpenBao — `sudo k3s kubectl -n apps describe externalsecret degoog-secret`; [`../platform/openbao.md`](../platform/openbao.md) |
